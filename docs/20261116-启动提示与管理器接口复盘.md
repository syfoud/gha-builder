# 2026-11-16 实机取证与接口复盘

## 已证实的两个问题

手机为 raphael，Android 13 / MIUI 14。同一套 ROM 刷入先前的 next 包后可进入系统，但出现“设备内部出现问题”。2026-11-16 17:41 的 ADB 采集获得了这次启动的完整 logcat、真实内核配置与各分区 VINTF 文件，没有刷写或重启手机。

启动日志原文：

```text
17:31:54.884 W VintfObject: Runtime info and framework compatibility matrix are incompatible: No compatible kernel requirement found (kernel FCM version = 3).
17:31:54.884 W VintfObject: For kernel requirements at matrix level 3, Missing config CONFIG_AUDIT
17:31:54.884 E Build: Vendor interface is incompatible, error=1
```

实机 `/proc/config.gz` 解压结果与之前交付的 next 构建 `.config` 字节一致，SHA-256 为 `7f0d9f8886f0a8ddcbea40ffdcb37e4a4b83fa30381e7ac2b97368a9e5d5c994`。其中 `CONFIG_AUDIT` 关闭。系统矩阵要求它开启，因此这条系统提示已定位到内核配置不满足 VINTF 要求。设备未提供 `checkvintf` 命令；本次结论依据实际 system_server / VintfObject 日志，而非该命令的输出。

对实机 matrix level 3、4.14 内核的 193 条适用配置要求逐项核对后，还发现以下共 13 项不匹配：

```text
AUDIT MODULES MODULE_UNLOAD MODVERSIONS
NETFILTER_XT_TARGET_NFLOG NF_CT_NETLINK
PPP PPP_BSDCOMP PPP_DEFLATE PPP_MPPE
PROFILING SECURITY_PERF_EVENTS_RESTRICT UID_SYS_STATS
```

这些名称均省略 `CONFIG_` 前缀，矩阵要求值均为 `y`。新增配置还需保留它们的 Kconfig 依赖。基底中 `SECURITY_PERF_EVENTS_RESTRICT` 不仅是关闭，而是其 Kconfig 与实现都已移除，因此还恢复 Android 对 `perf_event_paranoid=3` 的实际限制代码。

原 Rikka 源码的 `kernel/Makefile` 把另一份 `sm8150-perf_defconfig` 嵌入 config_data.gz。先前重建已改为公开真实 `.config`；这使裁剪配置与 ROM 的矛盾暴露。修复方案是让实际编译功能满足矩阵，继续公开真实配置。不能据此推断原始 2005 二进制的全部源码和构建条件。

## “管理器版本 5，要求 6” 的含义

数字是 **UAPI 接口版本**，并非 APK 的发行版号。Next 管理器的中文翻译也使用“KernelSU 管理器”字样，因此不能只凭这句文案认定安装了另一项目的管理器。

- 先前使用的官方 legacy 开发提交 `e5f5ec998de88b9fc43c62cff8f7ae12d3f4800a`：UAPI **6**。
- 正式发行版 Next **v3.4.2**，提交 `4c706b5938665866ebe16944a481a7b91e3396af`：UAPI **5**。
- 普通版管理器：`KernelSU_Next_v3.4.2_33355-release.apk`。
- APK SHA-256：`774a5511f7034a4930e881114e202319cbdc34c5aaaa5c7c6b6d2902364e4c58`。

之前将开发内核与正式版管理器配套推荐，没有核对 UAPI，导致不兼容。本次固定正式版 UAPI 5，并验证整个 `uapi/` 目录与正式发行标签的文件哈希一致。

v3.4.2 原始源码采用面向较新内核的挂钩方式，没有直接供 4.14 使用的手动挂钩配置。本次是在 v3.4.2 基线上移植官方冻结的 `v3.4.0-legacy` 提交 `8af3d4fec33be32fa5d3f8dae4f380fac45bf2cd` 中的必要旧内核兼容代码，属于带移植补丁的重建。移植文件列表、修改后的源码补丁、实际配置与构建身份保存在构建证据中。SELinux 旧策略读写锁的临界区保持禁止抢占，临界区内分配使用非睡眠方式。

## SUSFS 接入范围

文件系统补丁参考 `Fansirsqi/raphael-kernel@2a723dc65ed70db121194b4b0da8215b3c5615c6` 的 SUSFS v2.2.0 NON-GKI 移植。该参考的 ReSukiSU 挂钩与原型不能直接覆盖 Next 挂钩；已保留 Next 的手动 VFS 与 LSM 路径，并单独接入 SUSFS 控制接口、策略 SID、挂载标记和初始化。

开启挂载隐藏、kstat、uname、cmdline、符号过滤与 SUS_MAP。关闭 SUSFS 日志、上游明确不推荐的 SUS_PATH 与实验性的 OPEN_REDIRECT；这些开关会在清单和真实配置中列出。内核编入功能不代表已配置所有规则，也不保证任何特定应用无法检测 root。

## SOVIET 参考与额外痕迹约束

原故障包的内核版本字符串对应 SOVIET `5e403f9f8b2b004eb2f6c1a41a9be8b40f2c3f44`。该提交的 `drivers/kernelsu/Kbuild` 固定 `KSU_GIT_TAG=v3.2.0`、`KSU_GIT_VERSION=2980`，计算版本 33130；这只是该定制树自报身份，不等于所有文件都与官方 v3.2.0 相同。

它的 `uapi/supercall.h` 没有新式 `KERNEL_SU_UAPI_VERSION` 字段，GET_INFO 是 version/flags/features 三个 u32。其 Kbuild 编入 tiny_sulog.o，正式版则使用 sulog 子目录。extras.c 及 CHANGE_MANAGER_UID、GET_SULOG_DUMP_V2、CHANGE_KSUVER、CHANGE_SPOOF_UNAME 等 toolkit 入口在官方 v3.4.2 中也存在，不能称作 SOVIET 独有扩展。此次不复制 SOVIET root 源码，使用正式版 extras.c 与 sulog；保留正式版 UAPI、签名校验和正式版 supercall 命令实现，只把其 kprobe 入口改接手动 syscall 钩子，避免导入旧兼容参考中已被正式版修正的用户指针处理。

Next legacy 的 `0b17f24246db5c80c056b92c15bcad2b77f1276e`（2026-10-17）引入 preinit、LOOKUP_SYMBOLS、PREINIT 标志，明确将 UAPI 5 改为 6。v3.4.2 是此前的发行版，因此两者接口不同是分支时间与功能差异，先前构建没有检查配套关系才导致用户遇到报错。此处不通过伪造版本数字消除提示。

用户要求避免额外暴露 root 特征：关闭 KSU_DEBUG 与 SUSFS 日志，不在 LOCALVERSION 中追加 next/susfs；不创建自定义 proc/sysfs 调试节点、不注册探针服务、不修改启动参数来标记 root。诊断探针只放在刷机 ZIP 的 diagnostics 内，安装器不把它部署到系统；由用户需要时手动运行。vmlinux/System.map、源码差异与编译日志保存在电脑端构建证据。上游 Next 自身接口与现有 root 用户态文件仍需实机权限及行为核查，不能声称零痕迹。

## 实机验收与失败复盘

1. 先备份可启动 boot，并保留安装器生成的 `/sdcard/Rikka-rescue/` 目录。刷包后先不更换 ROM 或同时加入其他 root 模块。
2. 使用正式版 Next v3.4.2 普通 APK。确认管理器的接口不兼容提示消失；再验证普通 root 命令与模块启动。旧版管理器、旧 ksud 或遗留模块的数据迁移需单独记录，不自动清除 `/data/adb`。
3. 开机后运行 `diagnostics/collect-android.py`，对比 VintfObject 和 Build 日志。193 条配置的离线检查不能替代实机的完整 HAL / VINTF 检查。
4. 如使用提供的 `root-api-probe`，通过已获授权的 `su` 执行。它只查询 Next GET_INFO 与 SUSFS 版本，不设置隐藏规则、不触发正常重启。预期 `ksu_version=33355`、`uapi_version=5`；SUSFS 包还应返回 `susfs_2_2_0_present=true`。
5. 若只有 SUSFS 包出问题，对照同基底、同正式版的无 SUSFS 包，并保留两次配置与启动日志，避免把所有变量一起更换。
6. 若无法启动，进入 recovery 后立即运行 `diagnostics/collect-recovery.sh`，保留 pstore、last_kmsg、recovery.log、失败 boot 镜像及安装器日志，再恢复备份 boot。pstore 持久化依赖设备实际保留的 RAM 区域；空目录不等于没有内核崩溃。
7. 构建失败保留完整 build.log、源码提交、编译器身份、最终 `.config`、源码前后差异。构建成功还保留精确匹配的 vmlinux、System.map、原生 DTB、boot 重打包验证报告及 SHA-256 清单，可用于解析同一次构建的崩溃地址。

| 43851600677 | 单目录编译没有先生成 SELinux flask.h | 在根模块和文件系统编译前生成 SELinux 头文件 |

# Rikka 4.14.336 / Next v3.4.2：SUS_PATH 构建

此分支从已交付且实机能启动的构建器 `8c3e911` 派生。固定 Rikka `222b8d42`、Next 正式版 `4c706b59`、4.14 兼容参考 `8af3d4fe`、原 SUSFS v2.2 NON-GKI 文件系统补丁和 clang r510928；保留既有 VINTF 配置修复。

本次启用 `CONFIG_KSU_SUSFS_SUS_PATH=y`。继续关闭 KSU_DEBUG、SUSFS 日志、OPEN_REDIRECT；Next 的完整 UAPI 目录仍按正式版 SHA-256 校验，不修改 UAPI 5。

构建必须通过实际内嵌 config 校验、四个 SUS_PATH API 符号校验、193 项 VINTF 配置要求、原生 DTB 与 boot 重打包校验。构建标识改为 2026-11-17 / #2，uname 后缀仍为 -Rikka-2005；文件名明确带 suspath，以区分原交付。

SUS_PATH 在 VFS 的路径查找和 readdir 上工作，不依赖 MediaProvider FUSE 回调。Rikka sdcardfs 的 upper inode 使用 lower inode 的 i_ino，readdir 转发到 lower 文件；实际隐藏仍须刷入后验证直接查询与父目录枚举，构建成功不能代替实机验收。

内核不内置 Scene 路径或自动安装规则。路径规则通过现有 SUSFS 用户态工具配置；路径隐藏范围依赖 SUSFS 的进程标记和 KSU“卸载模块”策略，不等同于 FuseHide 的每包规则。确认本应用自身数据访问、系统文件管理器和 MediaProvider 行为后再持久化规则。

失败时 Actions 的 always 步骤上传日志、最终配置、补丁、构建身份以及已产生的 vmlinux/System.map。回退使用上一版已验证能启动的 boot/卡刷包；当前安装器继续先备份 boot，再写入及回读核验，不刷 dtbo/vbmeta、不清模块数据。

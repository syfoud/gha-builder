# Rikka 2005 + KernelSU Next：验收和失败复盘

这条构建以 Rikka 4.14.336 的 `222b8d42dde3f13973357cae50359fa2aca8239d` 为基底，接入 Next `legacy` 分支固定提交 `e5f5ec998de88b9fc43c62cff8f7ae12d3f4800a`。它是接近原版 2005 的源码重建；原二进制未公开完整构建配置和源码身份，因此不能声称逐字节复刻原版或全部未公开修改。

## 为什么重做

用户提供的故障结果 `raphael-ksunext-anykernel3.zip` 内层实际为 `raphael-2005slim-ksunext-20261115-1602-safe.zip`。它使用 SOVIET 4.14.357 内核，尾部拼入原版 2005 的整个 DTB，还叠加 safe 裁剪。这个组合无法代表“原 2005 只升级 root”。ZIP、gzip、FDT 基本结构未损坏，KSU 也确实编进去了；没有设备启动日志，不能据此锁定唯一 panic 点。

故障源码的 `kernel/Makefile` 还将 IKCONFIG 输入固定为 `raphael-vts_defconfig`，导致从 Image 解出的配置与 Actions 实际配置不符。新基底也有类似固定 defconfig 的做法，本次已改回最终 `.config`，打包前必须验证内嵌配置完全一致。

**另外复现了安装器的具体错误：** 用包内 ARM `magiskboot` 在 qemu-arm 下，对与所给 boot.img 同为 v0/4096 页/无 ramdisk 的夹具执行拆包、替换 Image.gz-dtb、重打包。旧流程没有清理拆出的 `kernel_dtb`，重打包后尾部实际含两棵 DTB，残留旧 boot 的树；修复后仅含一棵本次源码生成的 DTB，Image、启动头参数保持正确。证据见交付 evidence 的 `boot-roundtrip.json` 和 `.log`。这个错误会让“ZIP 中 DTB 正确”失去保证最终刷入 DTB 正确的意义，但仍需实机日志确认它在此次卡米中具体如何触发。

## 两个包

| 包 | 用途 | 差异 |
|---|---|---|
| `next` | 目标 root 方案 | 内建 Next legacy，使用手动 hook |
| `control` | 启动故障对照 | 同一 Rikka 基底，关闭 KSU |

两个包均使用本源码生成的原生 DTB，逐项核对原 2005 的 CPU 容量/能耗表/频率表、UFS QoS、CMA、vendor fstab；不叠加原 safe/plus 裁剪，不写 dtbo。保留 Rikka 的 CASS、MGLRU 等原有功能配置；新增 KALLSYMS 和 pstore 等取证能力。具体差异以每次产出的 `config-diff.txt`、`kernel-final.patch`、`ksu-final.patch` 为准。

本次已完成编译和全部打包校验。内核为 `4.14.336-Rikka-2005-next`，Next 报告 `v3.4.0-legacy` / `33327`，编译器为固定提交的 Android Clang 18.0.0；41 项关键 DTB 属性一致。编译 evidence 来自 [43775863832](https://github.com/syfoud/gha-builder/actions/runs/43775863832)；该次编译成功后被测试夹具错误挡在打包阶段，修正夹具后复用相同 Image，最终 [43776614273](https://github.com/syfoud/gha-builder/actions/runs/43776614273) 两套打包任务全部成功。手机启动和实际 root 授权尚未测试。

本地下载后的完整复核还确认：两套内核从源码生成的 DTB **与原 2005 DTB 逐字节相同**，共 2,909 个节点、13,479 项属性；不是只让 41 个调参键相同。每套最终 evidence 的 47 个文件以及父构建 evidence 的 33 个文件校验值全部一致。交付目录的 `verify_delivery.py` 可用 Python 重新核验，`verification.json` 记录结果。

Next 的当前主线版本不等于适用于 4.14 的版本。这里选官方 legacy 分支的固定提交，保留其兼容层；不是把只适用于新内核的主线代码直接覆盖进旧树。保留旧手动调用点，补上 reboot 用户态通信入口与 init.rc 的 fstat 回调。

## 刷入前

1. 先确认当前 ROM 能用的 boot 已恢复并能正常启动。备份一份“确定能启动”的 boot 到电脑。安装器只能备份刷入前的状态，如果刷入前已经卡米，它备份的同样是坏 boot。
2. 记录手机型号、ROM 名称、Android 版本、vendor 来源、原版 2005 是否能正常启动、当前 root 方案和模块列表。
3. 校验刷机 ZIP 附带的 SHA256。解开 Actions 下载的外层 artifact ZIP，刷里面的 AnyKernel ZIP。
4. 在可解密 `/data` 的 recovery 中安装。安装器必须先将 boot 备份并比对到 `/sdcard/Rikka-rescue/<时间>-<类型>/boot-before.img`，无法备份就中止。将该目录复制到电脑。
5. 首次验收先禁用现有 root 模块；不要同时更换 ROM、vendor、dtbo 或安装新模块，否则无法归因。

## 成功验收

- 进入桌面后保存 `uname -a`、`/proc/version`、`/proc/config.gz`、`getprop`、`dmesg`、`logcat -b all -d`。
- 安装 KernelSU Next 官方签名的管理器；管理器显示内核已接入且可授权，给测试终端授权后执行 `su -c id` 得到 `uid=0`。
- 检查 Wi-Fi、移动网络、蓝牙、摄像头、指纹、充电、休眠唤醒；正常后再逐个恢复模块。
- 编译成功、存在 KSU 符号、管理器 APK 能安装，都不能代替启动和 root 实测。

## 如果卡米

1. 记录刷入文件 SHA256、等待时间、是否循环重启、停在第一屏还是系统动画。拍下 recovery 安装输出中备份路径。
2. 直接进入 recovery，先取证，再恢复；尽量不反复启动系统、不清日志、不清数据。
3. 从 ZIP 中取出 `diagnostics/collect-recovery.sh`，电脑执行：

   ```powershell
   adb push collect-recovery.sh /tmp/collect-recovery.sh
   adb shell sh /tmp/collect-recovery.sh
   adb pull /sdcard/Rikka-rescue ./Rikka-rescue
   ```

   保存 pstore（如果存在）、last_kmsg（如果存在）、recovery 日志、当时 boot、recovery 的 cmdline/iomem。**recovery 的 dmesg 是 recovery 自身日志，不能当成故障内核的启动日志。**
4. 使用本次刷入前且已确认可启动的 `boot-before.img` 在 recovery 的“刷入镜像 → Boot”恢复。也可在确认 boot 分区及镜像来源后执行 `fastboot flash boot boot-before.img`，然后重启。不要把镜像写到 dtbo 或 recovery。
5. 保存完证据后，使用 `control` 包做一次单变量对照：

| 原版 2005 | control | next | 优先调查 |
|---|---|---|---|
| 可启动 | 可启动 | 失败 | Next hook/SELinux/init.rc、用户态或旧模块残留 |
| 可启动 | 失败 | 失败 | 重建基底与原版差异、工具链、配置、DTB 与 ROM/vendor 适配 |
| 失败 | 未测 | 未测 | 先建立与当前 ROM 匹配的已知良好 boot |
| 可启动 | 可启动 | 可启动但无 root | 管理器签名/版本、reboot 通信、授权及 ksud 启动 |

## pstore 的现实限制

本轮编入 PSTORE_RAM/CONSOLE/PMSG，但原 2005 设备树没有 ramoops 保留区。为避免任意物理地址破坏启动，本轮不凭空占用内存，因此**不保证卡米后一定有 pstore**。硬死锁也可能不产生 panic 记录。

如果第一次仍失败且无日志，下一轮先根据该设备正常系统的 `/proc/iomem`、启动后实际 DTB 和保留内存列表选择可用区域，再为 next 和 control 配置相同的 ramoops 地址、大小、console/record/pmsg 划分，并确认 recovery 也能读取同一区域。之前随意注入的 0xa1600000 方案缺少设备运行时内存证明，不能当成已经可靠的取证通道。必要时启用串口或 Qualcomm ramdump；这些需要设备侧条件。

## 每次构建必须留下什么

本次首轮构建已经验证了一个实际构建失败：`fs/namespace.o` 在 23:30:46 UTC 编译，Next 直到 23:36:54 UTC 才补入 `path_umount`，23:39:51 UTC 链接报缺符号。日志和失败 evidence 已保留。修复方式是在任何 C 编译之前单独解析 KSU Kbuild，完成全部兼容补丁，并比对编译前后源码，拒绝混合状态的产物。这是本次重建遇到并修复的问题，不能冒充用户原先卡米的已证实原因。

Actions 无论编译成功还是失败均上传 evidence：固定源码/Next/工具链/构建器提交、完整构建日志、原始及最终配置、配置差异、构建前后全部源码差异、编译器版本。成功时还保存 Image、原生 DTB、System.map、vmlinux、包清单及 SHA256SUMS。

将本机失败记录与该次 evidence 配对。用对应 vmlinux/System.map 解析 Oops 的函数偏移；修补一个变量后生成新包和新身份，不能覆盖同名文件后沿用旧校验值。Actions artifact 仅保留 30 天，应及时下载到本地归档。
